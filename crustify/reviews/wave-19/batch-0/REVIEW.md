# Review: libgit2 / core / wave 2 / batch 0 (symbol: `git_trace_set`)

Reviewed commit `6ccd53a97` (wave base). The item landed in `943038c1d` (wave 2
batch 0) as `unsafe fn set(TraceLevel, TraceCallback)` and `unsafe fn clear()` in
`crustify/rust/libgit2/libgit2/core/trace.rs`, both anchored `Wraps: git_trace_set`,
with a level above `None` and no callback (C's `GIT_ASSERT_ARG` refusal, an abort in
a debug build) made unrepresentable. The orchestrator's BSan gate on wave 2 passed
(no `bsan-gate.log`).

| step | outcome |
|---|---|
| lifecycle discovery | not applicable: a symbol-route batch with no type or raw-lifetime item, and `git_trace_set` is no lifecycle routine (it stores a level and a function pointer, allocates and frees nothing). |
| wavefront findings | the `callback` finding (by-value function pointer, borrowed for as long as it stays installed, never released, nullable only with `level == 0`, unlocked global, callback re-read after its NULL check) was re-verified against `src/libgit2/trace.c:16-23` and `src/libgit2/trace.h:22-49` and holds; the only `git_trace` callers in the campaign builds are `transports/httpclient.c` (DEBUG and TRACE) and, under the out-of-scope SecureTransport stream, `streams/stransport.c:269`, as the wave 1 review recorded on `git_trace_cb`. Nothing to resubmit; no report. |
| safe boundary | both wrappers must stay `unsafe`: libgit2 reads the configuration without a lock from whichever thread runs a traced operation, so a safe `set` or `clear` would let two safe calls race (a C11 data race, and for `clear` a NULL call through the check-then-re-read in `git_trace`), and the wrapper cannot serialise against readers inside C. The invalid pair is unrepresentable (`compile_fail,E0308`), the `trybuild` case requires `unsafe` for both, and `crustify scan-unsafe --name git_trace_set` finds no raw-pointer or dereference site. 1 report, fixed: `unsafe/set-clear-contract-excludes-calls-not-presence` — the `# Safety` text excluded other threads that "call into libgit2 while this runs", which on a strict reading leaves out a thread that entered `git_remote_connect` *before* the call and is still tracing inside it (the realistic race), and said nothing about synchronising later entries with the write. The contracts now exclude any other thread *inside* libgit2, whether it entered before or during, and require a later entry to synchronise with the call; the calling thread may itself be inside, in a traced call or in the callback. Regression: `tests/ub_unsafe/trace.rs::config::set_and_clear_while_a_traced_thread_waits_outside_libgit2`. The `common.rs` option setters share the old sentence; outside this workset, noted in the report. |
| UB | no candidate survived. Within the contracts, `set` passes a named level and a never-NULL function that is callable for the rest of the process (`TraceCallback`'s guarantee, strengthened by the wave 1 review for exactly this use); `clear` passes `GIT_TRACE_NONE` and NULL, the one pair C accepts without a callback; neither touches the error state on success, so both are safe before `git_libgit2_init` (`tests/ub_unsafe/trace.rs::config::set_and_clear_before_init`); reconfiguring from the callback on the tracing thread is allowed because `git_trace__write_fmt` works on a local copy of the callback and the message it owns. The whole workspace is clean under plain, ASan/UBSan (with LSan), TSan (`-Zbuild-std`) and BSan after the change; Miri is clean on every Rust-only trace test (inline and in the three integration suites). |
| equivalence | no defect: `tests/equiv/trace.rs::config` runs a 14-step `set` / `clear` sequence through `git_trace_set` and through the wrappers (over the adopted C recorder and over a `Tracer`), comparing the status, the thread's error state and the messages one HTTP connection reports after every step; it also reconfigures from inside the callback both ways and installs before `git_libgit2_init`. Documented divergences, unchanged: C accepts any `git_trace_level_t` value above the named ones (and behaves as `Trace` for them), which `TraceLevel` cannot name; and C's refusal of a level without a callback (`-1`, or an abort in the debug build) has no Rust counterpart because the pair does not type-check. |
| internal | none: the wrappers are two FFI calls with a `debug_assert_eq!(rc, 0)` each, which cannot fire for the arguments they pass; the trampoline, levels and errors they rely on were covered line by line by the wave 1 review. |
| conventions | 1 report, fixed: `conventions/equiv-mark-error-safety-note-split` — `tests/equiv/trace.rs::config::mark_error` had its `// SAFETY:` comment separated from the `unsafe` block by rustfmt's `let rc =` line break, which the campaign's lexical scan counted as undocumented (clippy accepted it). Otherwise clean: the batch's files are rustfmt-clean, `cargo clippy --workspace --all-targets` is clean, the names drop the `git_trace_` prefix the module supplies, and the duplicated `Wraps: git_trace_set` anchor is intentional (two wrappers, one for each valid contract of the C function). |
| misc | none. |
| coverage | C (gcov of the `coverage` build, private `GCOV_PREFIX`, whole workspace): `git_trace_set` 7/7 lines, 3 of 4 branches — the untaken one is `GIT_ASSERT_ARG`'s refusal, an `assert(3)` abort in this build and unreachable through the wrappers; `git_trace` and `git_trace__write_fmt` (inlined into `httpclient.c`) 15/15 lines, the untaken branch being "level allows, callback NULL", which `git_trace_set` never stores and only a race could produce. Rust (`cargo llvm-cov`, `coverage` variant): `core/trace.rs` has no uncovered line. No gap to fill. |
